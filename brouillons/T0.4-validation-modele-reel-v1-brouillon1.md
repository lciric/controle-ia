## Hypothèse

**Objet** (brief v2, T0.4 ; porte G0, critère 1 : « Harnais validé : déterminisme, équivalence d'activations, gardes testées »). Le harnais est validé sur un modèle jouet à poids aléatoires, sur processeur. Il garde-t-il ses propriétés sur le modèle réel de l'agent, sur processeur graphique, en demi-précision ?

**Ce que le harnais fait.**
- Les épisodes se jouent par lots, en pas synchronisés. À chaque (pas t, agent i), les actions de tous les épisodes du lot sont générées ensemble.
- Chaque transcription est une suite d'identifiants de jetons, jamais retokenisée, mise en forme par le gabarit de conversation du tokeniseur.
- Les activations viennent d'une passe avant unique sur la transcription complète. Elles sont prises en sortie des blocs de décodeur 7, 15 et 23 (fractions ¼, ½, ¾ de 32 couches).
- Sur un échantillon d'actions, la génération capture aussi ses propres activations. Une garde les compare à celles de la passe unique.

**Énoncés testés.**
- **H-format** : la transcription incrémentale coïncide, jeton pour jeton, avec le rendu complet du gabarit du modèle sur une conversation de contrôle.
- **H-logique** : en simple précision, les activations de génération et de passe unique coïncident à la précision du calcul près. La logique du harnais (alignement des positions, remplissage, masques, format) est donc exacte.
- **H-production** : en demi-précision bfloat16, l'écart entre ces activations reste du bruit d'arrondi, sous le seuil de production.
- **H-garde** : décalée d'un jeton, la même comparaison dépasse nettement le seuil, dans les deux précisions. La garde voit un désalignement.
- **H-déterminisme** : à graines et plan de lots identiques, sur la même machine, un rejeu redonne au bit près trajectoires, activations par jeton, vecteurs d'action et scores de sondes. Cela vaut dans le processus et entre deux processus.
- **H-stockage** : le disque rend exactement ce qui a été calculé en ligne. Une valeur stockée coûte 2 octets.

**Ce que ce n'est pas.** Aucune mesure de fond : l'environnement est l'environnement jouet du harnais et les sondes sont aléatoires. Comme pour T0.3, il s'agit de vérifications de l'instrument. Le débit, la mémoire et les projections sont descriptifs ; ils servent au devis des tâches suivantes.

**Pourquoi ces seuils** (fixés par raisonnement, avant toute donnée du modèle réel) :
- **1e-4 en simple précision.** L'arrondi unitaire vaut 2⁻²⁴ ≈ 6e-8. Les noyaux diffèrent entre génération (une ligne à la fois, avec cache) et passe unique. Après 32 couches, l'écart attendu reste de 1e-7 à 1e-5. Sur le modèle jouet, il valait 1,2e-7. Une erreur de logique (position, masque, jeton) donne des écarts d'ordre 1 : 1,8 pour le décalage d'un jeton sur le modèle jouet.
- **0,1 en demi-précision.** L'arrondi unitaire de bfloat16 vaut 2⁻⁸ ≈ 3,9e-3. Des noyaux différents produisent des écarts d'arrondi qui se propagent sur 32 couches. L'écart relatif par jeton (norme sur 4 096 dimensions) attendu est de l'ordre de 1e-2 au plus. Le seuil laisse un ordre de grandeur de marge. Sur le modèle jouet en demi-précision, le maximum valait 3,5e-3, et le décalage d'un jeton 1,76.
- Ces chiffres jouets ne prédisent pas le modèle réel. Ils montrent seulement que le code sépare les deux régimes.

## Métrique

- **Écart relatif par jeton**, couche ℓ, jeton n : d_n = ‖g_n − p_n‖₂ / ‖p_n‖₂.
  - g : activations capturées pendant la génération. p : activations de la passe unique.
  - Calcul en double précision, depuis les valeurs capturées converties sans perte en simple précision.
  - Statistique d'une action : maximum de d_n sur toutes les positions capturées. Ce sont les positions du contexte, sans le remplissage, et celles des jetons générés effectivement relus par le modèle.
  - Statistique d'une phase : maximum sur les actions comparées et les 3 couches (P2, P4).
- **Écart décalé d'un jeton** : la même mesure entre g_n et p_{n−1}. Statistique d'une phase : minimum sur les actions et les couches (P3, P5).
- **Empreintes** (sha256), par épisode :
  - trajectoire : identifiants de jetons et empans, en JSON canonique ;
  - activations par jeton : octets simple précision, par agent et par couche ;
  - vecteurs d'action : maximum par coordonnée ;
  - scores de 6 sondes linéaires aléatoires (3 couches × maximum ou attention), en double précision.
  - S'y ajoute l'empreinte des poids du modèle chargé en demi-précision.
- **Comparaisons** : égalité exacte des empreintes.
- **Descriptifs**, sans seuil :
  - jetons générés par seconde, par phase et par taille de lot (1, 8, 32) ;
  - jetons de passe unique par seconde ;
  - pic de mémoire du processeur graphique par phase ;
  - projection des heures et du stockage pour 2 000 épisodes, au rythme et aux longueurs mesurés.

## Plan d'analyse

- **Machine.**
  - Une instance avec un processeur graphique. Référence du devis : A100 80 Go ; une H100 80 Go convient aussi.
  - Pilote compatible avec CUDA 13.0 (roue figée de torch 2.14.1). À défaut, la même version construite pour CUDA 12.8, consignée au manifeste.
  - Au moins 32 Go de mémoire vive et 60 Go de disque.
  - Les runs A et B tournent sur la même instance.
- **Modèle.** `meta-llama/Llama-3.1-8B-Instruct`.
  - Révision R : le commit courant du dépôt du modèle au moment du run A, résolu par `HfApi().model_info(...).sha`.
  - R est passée en argument et consignée dans la configuration du manifeste. Le run B reprend R.
  - R devient la révision figée du programme ; elle est consignée dans `registres/decisions.md`.
  - Le gabarit reçoit une date d'en-tête figée (`date_string` = « 26 Jul 2024 »).
- **Graines (R9).** Entropie neuve au run A (`numpy.random.SeedSequence`), consignée au manifeste. Le run B reprend la même par `--rejeu-de`. Une graine par action, dérivée par tâche.
- **Phases du run A** (un processus) :
  1. **Format** : garde sur une conversation de contrôle de 3 tours.
  2. **Logique**, simple précision (poids chargés en bfloat16, convertis sans perte) :
     - 2 épisodes, N = 2 agents, T = 3 pas, 64 jetons au plus par action ;
     - lots de 2 ;
     - les 12 actions dans l'échantillon d'équivalence.
  3. **Production**, demi-précision :
     - 16 épisodes, N = 2, T = 10 (320 actions), 256 jetons au plus par action ;
     - lots de 8 ;
     - échantillon d'équivalence : les 40 actions des épisodes 0 et 1 ;
     - activations par jeton conservées pour les épisodes 0 et 1 (codage bfloat16-bits) ; vecteurs et scores pour tous ;
     - relecture du disque ;
     - rejeu du lot 0 dans le processus ;
     - empreinte des poids.
  4. **Débit** : génération seule, sans arrêt anticipé, de 128 jetons, sur des contextes de production tronqués à 2 048 jetons, pour des lots de 1, 8 et 32.
- **Séquence.**
  1. Run A.
  2. Commit local de ses résultats (le run B exige un arbre propre).
  3. Run B, avec `--rejeu-de` : il rejoue tout et écrit la comparaison scellée `diag/<run B>/comparaison-<run A>.json`.
  4. Rapatriement des résultats dans le dépôt. Les gros tableaux restent sur le volume de l'instance, sous `donnees/` ; leurs empreintes figurent dans les résultats scellés.
  5. Arrêt de l'instance par son identifiant (R10), consigné dans `registres/arrets.md` et `registres/depenses.md`.
- **Lecture.**
  - Le code l'applique : `lire` dans chaque résumé, `comparer_runs` pour P7.
  - Un sous-agent neuf, ni auteur de ce préenregistrement ni de l'analyse, la vérifie et prononce la preuve du critère 1 de G0 contre la table ci-dessous (R13).
  - Aucune correction pour comparaisons multiples : les contrôles sont déterministes.
