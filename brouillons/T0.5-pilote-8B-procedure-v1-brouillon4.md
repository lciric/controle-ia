## 2. Contrôles avant toute dépense

`COMMIT` est le commit de scellement du préenregistrement du pilote : celui qui a ajouté son empreinte compagnon.

```
COMMIT=$(git log --diff-filter=A -1 --format=%H -- prereg/T0.5-pilote-8B-v1.md.sha256)
git show "$COMMIT":scripts/amorce_instance_t05.sh | sha256sum      # doit égaler l'empreinte citée en tête du préenregistrement
git show "$COMMIT":scripts/pilote_t05_instance.sh | sha256sum      # idem
git diff --stat <commit du code cité> "$COMMIT" -- . ':(exclude)prereg' ':(exclude)brouillons' ':(exclude)registres' \
  ':(exclude)docs' ':(exclude)diag' ':(exclude)runs' ':(exclude)donnees' ':(exclude)livrables' ':(exclude)papiers' \
  ':(exclude)traces' ':(exclude)CLAUDE.md'                        # doit être vide
T=<chemin des tâches>
git cat-file -e "$COMMIT:$T" && git cat-file -e "$COMMIT:$T.sha256"   # dans l'arbre du commit (ajout forcé, N-014 (a))
[ "$(git show "$COMMIT:$T.sha256")" = "$(git show "$COMMIT:$T" | sha256sum | cut -d' ' -f1)  $(basename "$T")" ]   # sceau entier (V-6)
git ls-remote --exit-code origin refs/heads/calcul/t05-pilote-reel-v1   # code 2 attendu (branche absente) ; au relancement, la branche du relancement
```

Le script de l'instance refait, avant toute installation :
- le contrôle de la branche neuve (trois issues) ;
- la lecture du préenregistrement : nombre de tests attendus, chemin de la configuration, chemin des tâches ;
- la présence de la configuration, du fichier des tâches et de leurs sceaux dans l'arbre du commit, puis leurs sceaux par le module de scellement du dépôt (une ligne, nom de base, empreinte : les règles du lanceur ; X-3).

Chaque échec arrête avec le code 2, consigné au journal (messages du contrôle de branche compris, avec la cause donnée par git ; X-8), avant de payer l'installation. Le lanceur refait ensuite, avant le manifeste :
- la garde de l'arbre gelé (commit cité) ;
- les gardes de citation : configuration par son empreinte canonique, fichier des tâches par son empreinte, entropie des graines ;
- le code importé depuis `src/` du dépôt.

Un refus coûte la mise en place : faire ces contrôles avant le lancement. Puis, sur le dépôt au commit de scellement :
- `problemes()` de `controle_ia.prereg` rend une liste vide ;
- les empreintes compagnons du préenregistrement, de la configuration et des tâches sont vérifiées ;
- `verifier-arbre` dit « arbre intact ».

Le préenregistrement doit contenir, mot pour mot, les lignes que lisent le script, le lanceur et la session (V-6) :
- « Commit du code d'analyse : `<40 hexadécimaux>` » ;
- « Configuration du pilote (empreinte canonique) : `<64 hexadécimaux>` » ;
- « Tâches du pilote : `<64 hexadécimaux>` » ;
- « Entropie : `<entier>` » ;
- « Chemin de la configuration : `<chemin>` » ;
- « Chemin des tâches : `<chemin>` » (sous `donnees/<run d'extraction>/`) ;
- « Tests attendus : `<entier>` » (toute la suite de `tests/` au commit de scellement ; dernière ligne de pytest exigée : « N passed[, M warning(s)] in X s[ (h:mm:ss)] », rien d'autre ; Y-4) ;
- les empreintes des deux scripts de l'instance, en tête (Y-3).

## 4. Lancement (mode « args »)

```
GO_ID=GO-2026-10-04-08 vastai create instance <offre> --raw --image python:3.11-bookworm --disk 80 \
  --env "-e COMMIT=$COMMIT -e HF_TOKEN=$HF_TOKEN -e GH_TOKEN=$CONTROLE_IA_GITHUB_TOKEN" \
  --entrypoint bash --args -c "echo $(git show "$COMMIT":scripts/amorce_instance_t05.sh | base64 -w0) | base64 -d > /root/amorce.sh && bash /root/amorce.sh" \
  2>&1 | python3 -c 'import json, sys
t = sys.stdin.read()
try:
    d = json.loads(t)
    print("succès :", d.get("success"), "; identifiant :", d.get("new_contract"))
except Exception:
    print("réponse illisible (non affichée, elle peut contenir des jetons) ; vérifier par vastai show instances")'
```

- `--raw` avant `--args`, qui reste le dernier argument. Une réponse « illisible » ne prouve pas un échec : vérifier par `vastai show instances` avant toute nouvelle création.
- `ETUDE` (défaut `pilote`), `MODE` (défaut `reel`) et `BRANCHE` (défaut `calcul/t05-pilote-reel-v1`) ne se passent pas au premier lancement : les défauts sont ceux du préenregistrement.
- Consigner aussitôt l'identifiant et l'heure de création dans `registres/etat.md`.
- L'amorce clone le dépôt au commit, puis lance `scripts/pilote_t05_instance.sh`. Celui-ci enchaîne :
  - le contrôle de la branche neuve, puis la lecture précoce du préenregistrement et des fichiers cités (section 2) ;
  - la mise en place ; en mode réel, l'arrêt si la carte n'est pas disponible pour torch ; les tests (la suite complète, tous réussis, dernière ligne conforme au nombre attendu) ;
  - le run, sous son délai externe ;
  - le commit des résultats et la poussée de la branche ;
  - la poussée des vecteurs sur `donnees/t05/<run>` ;
  - les traces scellées.
- Délais figés :
  - le run reçoit TERM à 270 minutes (16 200 s), puis KILL cinq minutes plus tard. La limite interne est `duree_max_s` de la configuration, plus courte (au plus 15 000 s ; le lanceur refuse au-delà) ;
  - l'amorce reçoit TERM à 300 minutes, puis KILL cinq minutes plus tard ;
  - **chaîne des limites** (Y-7) : la surveillance fait arrêter l'instance 17 700 s après sa création (section 5). Démarrage, mise en place, tests, run (au plus 15 000 s), dernier lot après l'échéance, arrêt consigné, commit et poussées doivent y tenir : il reste au moins 2 700 s hors du run : démarrage et clonages (non mesurés) ; mise en place (environ 3 minutes : T0.4 v3, de la ligne « AMORCE » à la fin de 206 tests, `traces/t04-instance-54476244-20261006-121128/journal.txt`, 2730b775…) ; tests (642 tests : 866 s sur le processeur de la session, commit `e6ce058` ; environ 15 minutes au plus) ; dernier lot après l'échéance, arrêt consigné, commit et poussées (poussée en 2 secondes dans T0.4 v3 ; vecteurs jusqu'à 95 Mo) (V-8, Z-3). Le plafond de l'amorce (300 minutes depuis son départ) ne vient jamais avant l'arrêt par la surveillance ; il sert si la surveillance ne tourne pas. **Risque résiduel déclaré** (Z-5) : le délai externe de 270 minutes ne vient avant l'arrêt par la surveillance que si le run démarre dans les 1 500 s après la création ; au-delà, un lot bloqué que l'échéance interne n'arrêterait pas laisserait l'instance arrêtée sans `arret.json` ni poussée. La répétition jouet (préalable 8) mesure le temps de la ligne « AMORCE » à la fin des tests.
- Tout arrêt après le manifeste laisse un `arret.json` scellé : étape, motif, partiel. Une sortie en échec non consignée déclenche le filet du script : consigner, verser les traces, pousser. Un arrêt avant l'installation (code 2) ne laisse que le journal de l'amorce : le lire par `vastai logs`, jetons masqués.

## 5. Suivi

- Surveillance par le script scellé de T0.4 (`docs/procedures/surveiller-instance-t04-v1.sh`), qui reconnaît les lignes de l'amorce de T0.5 (mêmes motifs : FIN, ÉCHEC D'AMORCE, REDÉMARRAGE, ÉTAT TERMINAL, PLAFOND).
  - Son plafond est de 6 heures depuis la date passée en deuxième argument. Pour le plafond de 5 heures moins 5 minutes, passer la date de création moins 3 900 secondes.
  - À sa sortie, quel que soit le motif, la session arrête l'instance aussitôt, par son identifiant (R10).
- Archiver le journal de l'instance (`vastai logs <ID> --tail 20000`, jetons masqués) dans `traces/`, scellé.
- Ne rien relancer avec un paramètre changé : il faudrait une version 2 du préenregistrement.
- Relancement :
  - **cause d'infrastructure** : une limite externe due à l'infrastructure, jamais l'échéance interne `duree_max_s` (Y-8) : réseau ; instance perdue ; mise en place si lente que la surveillance arrête l'instance avant la fin du run ; dépôt distant injoignable au contrôle de la branche. Un seul relancement à l'identique, sur une instance neuve, avec `-e BRANCHE=calcul/t05-pilote-reel-v2` (contrôlée d'abord par `git ls-remote --exit-code`, code 2 attendu) ; il tient dans le reste du devis, sinon nœud. Les tests du script ne dépendent pas de `BRANCHE` (X-1, Y-1). Après un relancement, seul le run relancé est lu ; le premier est gardé comme trace ;
  - **préséance** (V-1) : un run dont `episodes.json` est écrit et poussé n'est jamais relancé, quelle que soit la cause de son arrêt, échéance interne comprise (cause déterministe : un relancement à l'identique s'arrêterait au même endroit) : il est lu tel quel, selon la table de lecture du préenregistrement, sur ses résultats scellés et non sur l'étiquette de l'étape ; un run sans `episodes.json`, arrêté par une cause d'infrastructure, est relancé une fois, sans nœud ; sinon, nœud ;
  - **cause déterministe** (panne de mémoire signalée par la bibliothèque, tests en échec, garde d'équivalence violée, fichier cité absent ou d'empreinte différente, mise en place hors réseau) : aucun relancement ; nœud. La panne de mémoire suit la règle du préenregistrement, qui reçoit ce risque de la revalidation (W-6) : arrêt consigné, nœud, pas de relancement sans nouvelle décision ;
  - **cause indéterminée** : aucun relancement ; nœud.

## 6. Fin

1. Arrêter l'instance par son identifiant : `vastai stop instance <ID>` (R10). Consigner l'arrêt dans `registres/arrets.md` et la dépense dans `registres/depenses.md`.
2. Récupérer la branche `calcul/t05-pilote-reel-v1` (ou celle du relancement), vérifier les empreintes (`verifier-arbre`, `sha256sum -c` dans chaque dossier de `traces/`), fusionner dans `main`, committer et pousser : la lecture exige un arbre propre (Y-6).
3. Récupérer la branche `donnees/t05/<run>` dans `donnees/` (hors git) et vérifier l'empreinte des vecteurs contre celle du résultat `episodes.json` (`vecteurs_sha256`). Si la poussée des vecteurs a échoué (journal), les fichiers sont restés sur le disque de l'instance arrêtée : nœud, comme pour N-012.
4. Les résultats et les vecteurs vérifiés, plus rien n'est sur l'instance : sa destruction se propose à Lazar le jour même. La session n'a pas le droit de détruire une instance (refus de la garde, R-060) ; c'est le geste de Lazar.
5. Lecture selon le plan gelé, par `lire_pilote.py` (Y-9), sous un run d'analyse distinct (`<run d'analyse>`), depuis la racine du dépôt :
   - `PYTHONPATH=src python -m controle_ia.environnements.lire_pilote preparer-etiquetage --run-pilote <run> --run-analyse <run d'analyse> --prereg prereg/T0.5-pilote-8B-v1.md --taches <chemin des tâches> --travail <dossier hors du dépôt>` ;
   - étiquetage : chaque lot remis à un sous-agent neuf, avec la consigne figée et les seuls fichiers du lot ; un lot non conforme est refait (`refaire-lot --run-analyse … --travail … --lot …`, même préfixe) par un nouveau sous-agent neuf, trois tentatives au plus, puis arrêt (nœud) ;
   - même préfixe (`PYTHONPATH=src python -m controle_ia.environnements.lire_pilote`, V-7) : `lire-etiquetage --run-pilote … --run-analyse … --taches … --travail …`, puis `analyser --run-pilote … --run-analyse … --taches …` ;
   - les sorties de chaque étape sont committées et poussées avant l'étape suivante (Y-6) ;
   - **gel des modules de lecture** (`MODULES_LECTURE`, dont `manifeste.py`, `gardes.py` et `scellement.py`, communs à d'autres tâches) : du scellement à la fin de la lecture, ils ne changent pas, même pour une autre tâche ; une modification qui s'imposerait est un écart au préenregistrement (nœud), décidé avant d'être faite.
6. Lecture contre les critères gelés par un sous-agent neuf, depuis les résultats scellés (R13 pour la partie qui touche le critère 2 de G0). Sceller, soumettre à Lazar.
