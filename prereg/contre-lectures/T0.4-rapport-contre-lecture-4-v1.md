### Q-1 — majeure — Tests en échec sur l'instance : le script meurt sur `tail -5` à deux fichiers, sans consigner l'arrêt ni pousser les traces (régression de M-4)

**Passages.**
- Brouillon : l. 210 (« P0 contraire … aucun run ; **traces poussées** ; diagnostic ; nœud ») ; l. 226 (« P0 contraire se lit dans les traces poussées … sortie des tests ») ; l. 255 (« Tests en échec sur l'instance : aucun run ; **traces poussées** ») ; l. 187 ; l. 82 (« sortie scellée »).
- Procédure : l. 77, l. 88, l. 92.
- Code : `validation_t04_instance.sh:16` (`set -euo pipefail`) et `:102-107` :
  ```
  if ! PYTHONPATH=src python -m pytest -q -p no:cacheprovider >"$TRAVAIL/tests.txt" 2>"$TRAVAIL/tests.err"; then
      tail -5 "$TRAVAIL/tests.txt" "$TRAVAIL/tests.err" | tee -a "$JOURNAL"
      journal "tests en échec : arrêt"
      consigner_arret "tests"
      exit 1
  fi
  ```
  Au commit 9aaf4a5, la ligne 82 n'avait qu'un fichier (`tail -5 "$TRAVAIL/tests.txt"`) et fonctionnait.

**Ce qui ne va pas.**
- GNU `tail` n'accepte la forme abrégée `-5` qu'avec un seul fichier. Avec deux, il sort avec 1 : « tail: option used in invalid context -- 5 ». Sous `pipefail`, le tube rend 1 ; sous `set -e`, le script sort aussitôt, avant `journal`, `consigner_arret` et la poussée.
- **Preuve** (s06, scénario `tests-ko`). Commit d'essai sur le dépôt nu local : 92e2f99 plus un test qui échoue ; amorce et script de 92e2f99.
  - Journal de l'instance : il s'arrête après la ligne de torch ; ni « tests en échec : arrêt », ni « ARRÊT pendant tests ».
  - Amorce : code 1 ; ce n'est ni 124 ni 137, donc pas de traces de l'amorce non plus.
  - Dépôt distant : **aucune branche poussée** ; ni journal, ni `tests.txt`, ni empreintes.
  - Seule la sortie de l'amorce (journal de l'instance) montre l'erreur de `tail` et les vingt dernières lignes de `tests.txt`.
- **Contre-épreuve** (s06, `tests-ko-corrige`) : même essai avec `tail -n 5` ; « tests en échec : arrêt », « ARRÊT pendant tests », traces scellées (empreintes conformes) et poussées.
- Ce chemin n'était couvert par aucun essai de l'auteur. Dans « plafond-tests », pytest meurt du TERM et le piège s'exécute avant la branche d'échec. La contre-lecture 3 l'avait vu fonctionner au commit 9aaf4a5 (r05, `tests_ko`).
- Portée :
  - aucun run ne part, aucun calcul n'est perdu, et la lecture « P0 contraire → nœud » reste applicable ;
  - mais la sortie des tests n'est ni scellée ni poussée, sur le chemin d'échec le plus probable de P0 (pytest en échec), contre trois phrases gelées ;
  - le diagnostic repose alors sur vingt lignes du journal de l'instance (liste des échecs tronquée s'il y en a beaucoup) et sur le disque de l'instance arrêtée, sans accès direct en mode « args ».
- Probabilité : faible. Aucun test ne dépend de la carte, aucun ne fige d'empreinte ou de valeur propre à la machine (recherche dans `tests/`). Mais c'est exactement l'événement que P0 doit couvrir.

**Correction proposée.**
- Code (recommandé) : `tail -n 5 "$TRAVAIL/tests.txt" "$TRAVAIL/tests.err"` (un caractère ; essai `tests-ko-corrige`). Ensuite :
  - nouveau commit cité ; mettre à jour l. 5, l. 14, la base du contrôle d'arbre de la procédure (l. 32) ;
  - rejouer les essais de la chaîne au nouveau commit, au moins le cas sain et les tests en échec (scénarios `sain`, `tests-ko` de s06, réutilisables) ; le code Python ne change pas : la répétition jouet peut être citée telle quelle, avec une phrase, ou refaite (une minute) ;
  - contre-lecture du seul différentiel.
- Texte (à défaut) : dire, l. 210, 226 et 255 et procédure l. 88, que des tests en échec (code non nul de pytest) arrêtent le script d'instance sans poussée ; la sortie des tests se lit alors dans le journal de l'instance (vingt dernières lignes), archivé et scellé par la session de pilotage, et sur le disque de l'instance arrêtée.
