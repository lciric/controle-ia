## C. Fautes nouvelles dans le code de lecture

- **`notes_alignees`** : pas de faux positif sur la chaîne réelle (`verif_2`).
  - Les notations sont produites par `demandes_de_notation` et `noter_ensembles` (modèle jouet). Les fiches passent par l'aller-retour JSON d'`ecrire_resultat`. Les textes contiennent des accents, un emoji, U+2028, CR LF et une tabulation.
  - L'empreinte du lanceur (`hashlib.sha256(d["ensemble"].encode("utf-8"))`, avec l'ensemble de `bilan["ensemble"]`, vide exclu par `strip()`) est exactement celle que recalcule la lecture (`_sha(f["bilan"]["ensemble"])`, même exclusion).
  - Artefacts tous arrêtés : C permuté, notation en trop (e2), notation d'un autre juge, notation d'un ensemble vide.
  - Limite : l'empreinte ne porte que sur l'ensemble, pas sur l'énoncé. Deux tâches au même texte d'ensemble ne se distingueraient pas. C'est improbable, et je n'en fais pas une remarque.
- **`_ouvrir_analyse` et `exiger_modules_cites`** (`verif_3`) :
  - les trois étapes passent par la ligne de commande, chemins relatifs, depuis la racine d'un dépôt jetable. Entre elles : commits de résultats, d'un registre et d'un module hors de `MODULES_LECTURE`. Aucun refus à tort ;
  - en revanche, une modification commitée d'un module commun de `MODULES_LECTURE` (`manifeste.py`), faite pour une autre tâche, bloque l'analyse. Le seul contournement laisse une provenance trompeuse (F-6).
- **`echantillon_d_etiquetage` et engagement** : déterministes.
  - L'engagement recalculé dans deux processus neufs (`PYTHONHASHSEED` 0 et 12345) est égal à celui qui est scellé (`verif_3`).
  - Les poids (`len(groupe) / k`) et l'ordre (strates triées, paires triées par clé, permutation tirée par graine) ne dépendent ni du processus ni du hachage.
  - Seule une montée de version de numpy entre deux étapes changerait les tirages, et donnerait un message trompeur (F-6).
- **`difference_kappas`** :
  - valeur ponctuelle égale à κ(directions) − κ(contrôles), recalculée à part ;
  - même tirage de tâches pour les deux groupes ;
  - tirages au kappa indéfini comptés (`verif_4` §4.2).
- **`intervalles_familles`** : même tirage pour les quatre mesures (deux mesures identiques donnent des intervalles identiques) ; tirages sans tâche comptés ; mesure sans tâche → `None` (`verif_4` §4.3).
- **`predictions` et `statut`** : conformes au texte (tests, et `verif_4` §4.4).
  - Les réfutations des sept prédictions sont disjointes de leurs confirmations : l'ordre « réfutée d'abord » est sans effet.
- **`lecture_juge`** : conforme. Plan B par l'incomplétude prioritaire ; nœud sous 48 tâches ou sur une part illisible ; décomposition impossible consignée sans arrêter (`verif_4` §4.4, tests).
- **`mesures_format`** : la nouvelle garde de longueurs ne peut pas se lever sur un run sain. `bilan["historique"]` a une entrée par action du journal (`propositions.py` l. 172-188, 271-278), et le journal est fait des mêmes actions que la fiche (`pilote_a.py` l. 122-127).

### F-6 (mineure) — Gardes de lecture : une modification d'un module commun bloque la lecture ; le contournement fausse la provenance ; « modifiés sans commit » ne décrit pas le code

**Où.** `lire_pilote.py` l. 82-85 (`MODULES_LECTURE`), l. 468-516 ; B4 l. 155, 211 ; `harnais/validation_reelle.py` l. 75, 244-248.

**Problème.**
- **(a) Blocage.** `MODULES_LECTURE` comprend des modules communs à d'autres tâches : `manifeste.py`, `scellement.py`, `gardes.py`, `propositions.py`, `rubrique.py`, `juges.py`, `lancer_pilote_a.py`.
  - Depuis le 1er octobre, ces fichiers ont reçu de 1 à 5 commits chacun.
  - Une modification légitime de l'un d'eux, entre le scellement du pilote et sa lecture, bloque toutes les étapes de lecture (« modules de lecture modifiés depuis le commit cité ») ; aucune procédure n'est écrite.
  - Cet arrêt est voulu par D-5 ; seul manque le chemin pour en sortir.
- **(b) Contournement et provenance.**
  - Le seul contournement — ramener ces fichiers à l'état du commit cité sans commit — passe la garde : la comparaison se fait au commit cité, arbre de travail compris.
  - `lecture.json` consigne alors `commit_courant` = HEAD, qui ne décrit pas l'arbre exécuté, et ne dit pas que l'arbre n'était pas propre.
- **(c) Formulation.** B4 l. 211 range « modifiés sans commit » parmi les arrêts. Le code n'arrête que sur un écart au commit cité : une modification non commitée qui ramène l'état cité passe. L. 155 (« identiques au commit cité (modifications non commitées comprises) ») est, elle, exacte.
- **(d) Version de numpy.** Les éléments de l'étiquetage se recalculent par `Generator.choice` et `permutation`. NumPy ne garantit pas leurs flux d'une version à l'autre. Une montée de version entre la préparation et la lecture de l'étiquetage arrêterait sur « éléments recalculés ≠ engagement », message trompeur. La version est consignée au manifeste d'analyse mais n'est pas comparée.
- **(e) Module hors de la liste.** `harnais/validation_reelle.py` porte la garde d'import et le motif de l'entropie, et n'est pas dans `MODULES_LECTURE`. L'y ajouter augmenterait le risque (a) : 12 commits depuis le 1er octobre.

**Preuve.** `scripts/verif_3_etapes.py` (dépôt jetable, trois étapes en ligne de commande) :
- `manifeste.py` modifié et commité pour une autre tâche : `ARRÊT : modules de lecture modifiés depuis le commit cité` ;
- le même fichier ramené à l'état cité sans commit : l'analyse passe ;
- `commit_courant` = HEAD, alors que `git status` montre `M src/controle_ia/manifeste.py`.

**Correction proposée.**
- Écrire la procédure : modules de lecture gelés jusqu'à la fin de la lecture, ou contournement permis et consigné.
- Consigner l'état de l'arbre (`git status --porcelain`) dans `etiquettes.json` et `lecture.json`, ou exiger un arbre propre à chaque étape.
- Comparer la version de numpy à celle du manifeste d'analyse, avec un message explicite.
- Écrire l. 211 comme l. 155.
